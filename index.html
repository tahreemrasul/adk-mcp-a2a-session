1 Overview

This guide introduces the components needed to build AI agents that act on external systems. It begins with the limitations of a language model used on its own, introduces tools and function calling as the mechanism that addresses them, and defines an agent as a model that chains tool calls to complete a task. It then covers three technologies: ADK, a framework for building agents; MCP, an open protocol for connecting AI applications to tools; and A2A, an open protocol for communication between agents.

All sections use one example: a currency-conversion capability. It is introduced as a Python function, used through function calling, given to an ADK agent, moved behind an MCP server, and finally offered to a second agent over A2A. The figure below shows the complete system.

2 The limits of a standalone LLM

A large language model takes text in and generates text out. Its knowledge comes from training data with a fixed cutoff date, and it has no connection to anything outside the conversation. On its own it cannot look up a current exchange rate, query a company database or send an email.

The answer in Figure 2 may be close, but the model cannot know today's rate. To answer correctly, it needs a way to reach live data and other systems.

3 Tools

A tool is a function that an application makes available to a model, such as an API call, a database query or a calculation. The model never sees the tool's code. It receives a description with the tool's name, its purpose and the parameters it accepts:

def get_exchange_rate(base: str, target: str) -> float:
    """Return how many units of `target` currency one unit of `base` buys."""
    ...

# What the model receives
{
  "name": "get_exchange_rate",
  "description": "Return how many units of `target` currency one unit of `base` buys.",
  "parameters": {
    "type": "object",
    "properties": { "base": {"type": "string"}, "target": {"type": "string"} },
    "required": ["base", "target"]
  }
}

Most model APIs, including Gemini, OpenAI and Anthropic, accept tool descriptions in this JSON Schema format. Libraries generate it from the function's name, type hints and docstring: the Google Gen AI SDK (google-genai) and ADK do this for any Python function, and the MCP Python SDK does the same through its @mcp.tool() decorator. A clear docstring therefore directly affects how well the model uses the tool.

5 Agents: function calling in a loop

The cycle in section 4 performs one function call. Consider the request "Convert 200 USD to GBP and to JPY". It needs two exchange rates, so one round trip is not enough. The application has to keep returning results to the model and asking again, until the model replies with text instead of another function call:

A system in which the model directs this loop is usually called an agent. Anthropic's Building effective agents draws the distinction this way:

Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage.Anthropic, Building effective agents

In a workflow, the developer defines the steps. In an agent, the model chooses them.

6 Agent Development Kit (ADK)

The loop in section 5 can be written by hand in about thirty lines. A production agent needs more than the loop:

  • conversation history and state that persist across turns
  • several agents that delegate work to each other
  • hooks for logging, guardrails and error handling
  • tools to test, evaluate and deploy

Agent frameworks provide these parts. The Agent Development Kit (ADK) is Google's open-source framework, available for Python, TypeScript, Go, Java and Kotlin. Other frameworks include LangGraph, the OpenAI Agents SDK, CrewAI and the Claude Agent SDK. ADK is optimised for Gemini, but it also supports other models through connectors such as LiteLLM.

Agents

Every agent derives from BaseAgent. ADK provides three kinds:

  • LlmAgent (also available as Agent) uses a model to reason, decide and call tools. This is the agent type from section 5.
  • Workflow agents run sub-agents in a fixed order without using a model for control flow: SequentialAgent (one after another), ParallelAgent (concurrently) and LoopAgent (repeatedly, until a condition or iteration limit).
  • Custom agents subclass BaseAgent for logic that does not fit either pattern.

An LlmAgent is configured with five main parameters:

ParameterPurpose
nameUnique identifier
modelThe model, such as "gemini-flash-latest" or a LiteLlm object for other providers
descriptionWhat the agent does. Other agents read it to decide whether to delegate to this one.
instructionThe prompt that guides its behaviour and tool use
toolsThe tools it can call

The currency function from section 3 becomes an agent like this:

from google.adk.agents import Agent

currency_agent = Agent(
    name="currency_agent",
    model="gemini-flash-latest",
    description="Converts amounts between currencies.",
    instruction=(
        "You convert amounts between currencies. "
        "Always use get_exchange_rate; never guess a rate."
    ),
    tools=[get_exchange_rate],   # the same plain function
)

Tools

  • Function tools: any Python function, wrapped automatically or explicitly with FunctionTool.
  • Built-in tools: such as google_search for grounding in web results, and code execution through BuiltInCodeExecutor.
  • MCP tools: every tool on an MCP server, through McpToolset (see section 7).
  • Agents as tools: AgentTool wraps another agent so it can be called like a function.

Multi-agent systems

Agents can be composed in two ways:

  • sub_agents (delegation): the parent's model reads each sub-agent's description and transfers the conversation to the best fit. Control passes to the sub-agent. Section 8 uses this with a remote agent.
  • AgentTool (invocation): the parent calls the other agent as a tool, receives its final answer as the tool result, and decides the next step itself.

Sessions, state and events

  • A session is one conversation. It stores the history and a state dictionary that tools and agents can read and write. Key prefixes set the scope: user:, app: and temp:.
  • Every step (a user message, model reply, tool call or tool result) is recorded as an event. The sequence of events forms the conversation history.
  • A session service stores sessions in memory, in a database or on Vertex AI.

Callbacks

Callbacks are functions that run before and after the agent, the model call, and each tool call (before_model_callback, after_tool_callback and so on). They are used for logging, guardrails, caching and modifying requests or responses. For example, a before_model_callback can block a request before it reaches the model.

Development tools

The adk command-line tool runs agents locally. adk web opens a browser UI for chatting with agents and inspecting their events, state and traces. adk eval runs evaluation sets, and adk deploy deploys agents to Google Cloud.

7 Model Context Protocol (MCP)

So far, get_exchange_rate exists only inside one Python program. Other AI applications, such as a chat client, a code editor or another team's agent, would each need their own integration for it. With many applications and many tools, every pair needs a separate integration.

The Model Context Protocol (MCP) is an open standard for this connection, open-sourced by Anthropic in November 2024. Its documentation compares it to a USB-C port for AI applications: a tool written once as an MCP server can be used by any application that supports MCP.

Core concepts

From the MCP architecture documentation:

  • Host: the AI application the user works in, such as an ADK agent, Claude Desktop or VS Code.
  • Client: a component inside the host that maintains the connection to one server. A host creates one client per server.
  • Server: a program that exposes capabilities to clients. It can offer three kinds:
    • Tools: functions the model can call (used in this guide)
    • Resources: data that provides context, such as files or database records
    • Prompts: reusable prompt templates
  • Transports: stdio for a local server that the host starts as a subprocess, and Streamable HTTP for a remote server.
  • Messages: clients and servers exchange JSON-RPC 2.0 messages, for example to list a server's tools or call one.

The currency tool as an MCP server

from mcp.server.mcpserver import MCPServer   # mcp 2.x; older tutorials use FastMCP

mcp = MCPServer("currency")

@mcp.tool()
def get_exchange_rate(base: str, target: str) -> float:
    """Return how many units of `target` currency one unit of `base` buys."""
    ...

mcp.run()

On the ADK side, the only change from section 6 is the tools list: tools=[McpToolset(...)] replaces the Python function. ADK starts the server, requests its list of tools and passes their descriptions to the model.

8 Agent2Agent protocol (A2A)

MCP gives an agent access to tools. Some tasks are better handed to another agent: one with its own instructions, model and tools, often maintained by a different team or built with a different framework. In the running example, a trip-planning agent needs currency conversion and delegates it to the currency agent.

The Agent2Agent protocol (A2A) is an open standard for this. It lets agents discover each other and exchange tasks over HTTP without knowing how the other is implemented. Google announced it in April 2025, and it is now governed by the Linux Foundation. The A2A documentation describes its relationship to MCP this way:

MCP is vertical. It deepens a single agent. A2A is horizontal. It connects agents across that boundary.A2A documentation, A2A and MCP

Core concepts

From the A2A key concepts:

  • Client agent and remote agent: the client acts on behalf of the user and sends work. The remote agent exposes an HTTP endpoint that implements A2A.
  • Agent card: a JSON document describing the remote agent's name, skills, endpoint and authentication requirements, served at /.well-known/agent-card.json.
  • Task: a unit of work with an ID and a lifecycle. It can complete, fail, or pause for more input.
  • Message: one turn of communication, made of parts (text, files or structured data).
  • Artifact: an output the remote agent produces, such as a document or structured data.

A2A in ADK

Each side takes one line. to_a2a() turns an agent into a web app that serves its agent card, and RemoteA2aAgent lets another agent use it as a sub-agent (see section 6):

# the team that owns the currency agent
a2a_app = to_a2a(currency_agent, port=8001)

# the team building the trip planner
remote_currency = RemoteA2aAgent(
    name="currency_agent",
    description="Converts amounts between currencies.",
    agent_card="http://localhost:8001/.well-known/agent-card.json",
)
trip_agent = Agent(..., tools=[get_hotel_price], sub_agents=[remote_currency])

ADK's guidance is to use A2A when the other agent is a separate service, owned by another team, or built in another language or framework. Agents that only organise code within one application should be local sub-agents, which share memory and avoid network calls.

9 Summary: choosing an approach

RequirementApproach
The model needs live data or must take an actionA tool, through function calling
The model should choose the steps itselfAn agent: function calling in a loop
Sessions, multi-agent delegation, evaluation and deploymentAn agent framework such as ADK
One tool, shared by many AI applicationsAn MCP server
Delegate a task to an agent run by someone elseA2A
